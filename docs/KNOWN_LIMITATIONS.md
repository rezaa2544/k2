## ۵. محدودیت‌های آگاهانهٔ دامنه (توضیح‌داده‌شده، نه نقص)

1. **همهٔ اعداد تجربی فرضیه‌اند.** حاشیهٔ ۲۰٪، سقف جبرانی ۳۰٪، آستانه‌های تسلط، ضرایب اولویت و بازه‌های مرور از مطالعهٔ این کاربر مشتق شده‌اند، نه از قانون علمی. همه در `config.py` با برچسب `[H]` و در تنظیمات قابل تغییرند.
2. **تاریخ رسمی آزمون حدس زده نمی‌شود.** نمونهٔ «۳۰ مهر» سال ندارد و سالی برایش ساخته نمی‌شود؛ وضعیت تاریخ (رسمی/تخمینی/نامشخص) کاربر تعیین می‌کند.
3. **تعارض یکشنبه باز می‌ماند** تا کاربر مشخص کند کدام کلاس واقعاً برگزار می‌شود (D-004).
4. **برنامهٔ نمونه داده است، نه منطق** (D-019).
5. **هیچ تشخیص پزشکی/روان‌شناختی** — نشانگر «فشار برنامه» فقط رفتار سیستم را توصیف می‌کند.
6. **بدون چت‌بات آزاد، استریک یا رتبه‌بندی** (NFR-01، NFR-02).
7. **هفتهٔ شنبه‌محور** — اگر کاربر هفتهٔ دیگری بخواهد، باید در `jdate.weekday_index` تغییر کند.

## ۶. مخزن و انتشار بسته

مخزن عمومی پروژه `rezaa2544/k2` و شاخهٔ اصلی `main` است. فایل قابل‌دانلود، بستهٔ کامل one-folder در `downloads/K2-windows-x64.zip` است؛ این آرشیو باید با `K2.exe` و پوشهٔ `_internal` یکجا نگه‌داری شود.

پس از push روی `main`، گردش‌کارها تست‌ها را اجرا می‌کنند؛ در صورت تغییر هر فایلی زیر `src/`، CI الزام می‌کند `preview/K2-preview.html` هم در همان تغییر به‌روز شود. سپس Windows CI، EXE را می‌سازد و headless اجرا می‌کند. فقط پس از موفقیت، ZIP کامل، checksumها و شناسهٔ commit داخل HTML preview را همگام کرده و همه را با `GITHUB_TOKEN` گردش‌کار به `main` push می‌کند. انتشار در GitHub Releases جداست و با tag نسخه (`v*`) به‌صورت draft ساخته می‌شود.

برای تغییرات بعدی، ابتدا تست‌ها را اجرا کنید، سپس commit و push معمولی انجام دهید:

```bash
cd /home/user/k2
PYTHONPATH=src QT_QPA_PLATFORM=offscreen python -m pytest tests -q
git status --short
git add <files>
git commit -m "<message>"
git push origin main
```

برای بررسی نتیجه، در GitHub Actions باید run مربوط به commit را بازبینی کرد؛ لینک دانلود مستقیم پس از موفقیت build به ZIP تازهٔ مخزن اشاره می‌کند. هیچ force-push یا بازنویسی تاریخچه‌ای لازم نیست؛ فایل ZIP کامل نیز نباید با EXE تنها جایگزین شود.
